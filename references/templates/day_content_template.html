📖 二、核心讲解

是什么：Embedding 与向量库一句话

Embedding = 把一段文本变成一串数字（一个向量），意思相近的文本，向量在空间里离得近。

向量库 = 存这些向量的数据库，最大本事是"给一个新向量，几毫秒内找出库里最像的 Top-K 个"。

大白话——embedding 把"意思"变成"坐标"，向量库像一个特别快的"意思-坐标"查表器。RAG 就是靠这两样，把用户问题翻译成坐标 → 查库 → 拿回相关文本 → 交给 LLM 生成回答。

🎓 给客户讲 Embedding 的三句话

1. 计算机不认识"文字"，只认识"数字"。Embedding 就是把每段文字翻译成 1024 维的数字向量。

2. 相近意思的文字，翻译出来的向量也相近——"投标截止日期"和"报名结束时间"，坐标几乎重叠。

3. 检索的时候，用户问句也变成向量，去库里找离得最近的 Top-K 段文字，扔给 LLM 生成答案。

□ □ □ 检索链路口诀 □ □ □
分块 · 嵌入 · 检索 · 重排 · 过滤
5 个维度按顺序调 · 每调一步都能量化收益

为什么：PM 视角下的三个大坑

🚨 坑 1 · 只调 Top-K 数值（治标不治本）

Top-K 检索答不出？很多人第一反应是 "把 K 从 5 调到 10 试试"——结果确实召回率涨了 5 个点，但 LLM 的输入被塞满了无关内容，答对率反而掉了 3 个点，整体指标只涨 2 个点。

治本的思路：先看是 分块碎片化（该调 Day 7 的分块策略），还是 embedding 模型选错（换中文优化的模型），还是 无重排（Top-K 顺序乱）。

正确姿势：Top-K 只在最后调，之前先把 chunk / embedding / rerank 调好。

🚨 坑 2 · 不做重排（Top-K 顺序未必最相关）

Embedding 向量检索是个"粗筛"——它算的是"表面语义相似"。真正的"回答相关性"要用一个专门的重排模型（Reranker）再判一遍。

举个真实场景：查询"招标保证金金额"，向量检索 Top-5 里第 1 名是"投标保证金要求"（讲要求，没写金额），第 4 名才是"投标保证金：500,000 元"。不做重排，你给 LLM 的是第 1 名，答案就是"文档没写具体金额"——但其实文档写了，就是没排上去。

正确姿势：Top-20 向量粗筛 → Reranker 重排取 Top-5 → 交给 LLM。多这一步，答对率经常涨 10-15 个百分点。

🚨 坑 3 · 忽略元数据过滤（用向量硬拼所有事）

用户问："2024 年的招标文件里哪些提到了 ESG 要求"。你直接把这个问句丢进向量检索——库里 2019、2020、2021 年的文件也全被检出来了，因为它们也讲 ESG。

这时候元数据过滤前置是标准姿势：先按 publish_date >= 2024-01-01 过滤到只剩 2024 年的分块，再对这批做向量检索——召回率立刻上一个台阶，还省算力。

正确姿势："能用元数据过滤解决的，别让向量硬拼"——这是 Day 7 元数据文化的红利。

🧭 PM 行动指南：检索质量评估 4 指标

Recall@K：Top-K 里包含标准答案的比例（前提要有测试集标注）——衡量"检得到"

MRR (Mean Reciprocal Rank)：标准答案在 Top-K 里的平均排名倒数——衡量"排得靠前"

NDCG：考虑相关性打分的加权指标——衡量"高相关的排得越前越好"

端到端答对率：找 30-50 条真实问答对，让完整 RAG 跑一遍，人工判分——衡量"客户真的用起来爽不爽"

PM 场景优先级：端到端答对率 > Recall@K > MRR > NDCG。指标越靠后越技术、越靠前越业务，跟客户对齐时永远先讲第一个。

怎么用：5 个优化维度（顺序有讲究）

1
Chunk 大小与重叠——256-512 tokens + 10-20% overlap 是主流甜蜜点。太短（< 100）信息不完整、太长（> 800）稀释语义。政企文档偏向 400-500 tokens。
2
Embedding 模型选型——中文场景首选 BGE-M3（开源、免费、效果好）或阿里云百炼的 text-embedding-v3（API、按量付费、更省心）。别再默认 OpenAI，中文场景吃亏。
3
检索相似度阈值——余弦相似度 0.7 起步。低于 0.5 基本是噪声。设个阈值兜底，避免"库里没有答案时硬拉 Top-K 编"。
4
重排 Reranker——推荐 BGE-Reranker-v2（开源）或 Cohere Rerank（API）。用法：向量检索出 Top-20 → 重排取 Top-5 → 给 LLM。这一步经常带来 10-15 分的答对率提升。
5
元数据过滤前置——按时间 / 来源 / 文档类型 / 标签先过滤，再对剩余分块做向量检索。这是 Day 7 元数据文化的直接红利。
⚠️ 顺序为什么这么排？

Chunk 在最前——分块碎了，后面全白搭。Embedding 第二——模型选错，向量本身就不对。阈值第三——是兜底，早设早止损。Reranker 第四——粗筛质量够好，才有精排的意义。元数据过滤第五——不是最后一步，是可以插在任何一步之前的"外挂"，尤其在数据量大的时候是首选。

Step 2 · 换 Embedding：ada-002 → 阿里云 text-embedding-v3

ada-002 是英文优化的，中文场景吃亏。换成阿里云百炼的中文 embedding。

import dashscope
from dashscope import TextEmbedding
import os

dashscope.api_key = os.getenv("DASHSCOPE_API_KEY")

def embed(texts):
    """批量把文本转成向量"""
    resp = TextEmbedding.call(
        model=TextEmbedding.Models.text_embedding_v3,
        input=texts  # 支持批量，最多 25 条一次
    )
    return [item["embedding"] for item in resp.output["embeddings"]]

# 对所有 chunks 重新嵌入
import json
chunks = json.load(open("chunks.json", encoding="utf-8"))
for i in range(0, len(chunks), 25):
    batch = chunks[i:i+25]
    vecs = embed([c["text"] for c in batch])
    for c, v in zip(batch, vecs):
        c["vector"] = v

指标变化：Recall@5: 71% → 79%（+8），答对率: 67% → 73%（+6）

Step 3 · 加相似度阈值 0.5

低于 0.5 的分块直接扔掉，不让它污染 LLM 上下文。

import numpy as np

def cosine(a, b):
    a, b = np.array(a), np.array(b)
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

def retrieve(query, chunks, top_k=5, threshold=0.5):
    q_vec = embed([query])[0]
    scored = [(c, cosine(q_vec, c["vector"])) for c in chunks]
    scored.sort(key=lambda x: x[1], reverse=True)
    # 阈值过滤：低于 0.5 直接丢
    return [(c, s) for c, s in scored[:top_k] if s >= threshold]

指标变化：Recall@5 微降到 78%（正常，牺牲一点召回换精度），答对率: 73% → 76%（+3，噪声减少）

Step 4 · 加重排 Reranker（Top-20 → 重排取 Top-5）

用阿里云百炼的 gte-rerank（也可以换 BGE-Reranker-v2）。

from dashscope import TextReRank

def rerank(query, candidates, top_k=5):
    """对向量粗筛的 Top-20 做精排"""
    resp = TextReRank.call(
        model="gte-rerank",
        query=query,
        documents=[c["text"] for c in candidates],
        top_n=top_k
    )
    # 按重排后的 index 取回原分块
    return [candidates[r["index"]] for r in resp.output["results"]]

# 使用姿势：向量检索 20 个 → 重排取 5 个
candidates = [c for c, _ in retrieve(q, chunks, top_k=20, threshold=0.5)]
top5 = rerank(q, candidates, top_k=5)

指标变化：Recall@5 = 85%（+7），答对率: 76% → 85%（+9）——单步收益最大的一环

Step 5 · 元数据过滤前置

用户问句里含"2024 年"、"XX 项目"这种关键词时，先按 metadata 过滤，再向量检索。

import re
from datetime import datetime

def parse_filters(query):
    """从用户问句里抽出可过滤的条件"""
    filters = {}
    # 抽年份
    year = re.search(r"(20\d{2})\s*年", query)
    if year:
        filters["year"] = int(year.group(1))
    # 抽项目名 / 文档类型 等，视业务定制
    if "招标" in query:
        filters["doc_type"] = "招标文件"
    return filters

def retrieve_with_filter(query, chunks, top_k=20, threshold=0.5):
    filters = parse_filters(query)
    # 先按元数据过滤，再向量检索
    filtered = chunks
    if "year" in filters:
        filtered = [c for c in filtered
                    if datetime.fromisoformat(c["metadata"]["publish_date"]).year == filters["year"]]
    if "doc_type" in filters:
        filtered = [c for c in filtered if c["metadata"]["doc_type"] == filters["doc_type"]]
    return retrieve(query, filtered, top_k=top_k, threshold=threshold)

指标变化：Recall@5 = 89%（+4），答对率: 85% → 88%（+3）

🧪 案例 C · 诊断这三个错误案例，分别是哪个维度出了问题？（自己练）

Case 1：查询"投标保证金金额"，检出 Top-1 是"第 3 章 投标保证金 · 交纳方式和退还流程说明，甲方要求乙方按招标要求提交..."（3800 字）。虽然相关但没有具体金额。

Case 3：查询"评标办法中综合评分法的权重分配"，向量检索 Top-1 是"评标办法有综合评分法和最低价法两种..."（讲介绍，没写权重）；库里其实有一段专门讲权重的，排在 Top-8。

查看参考答案

Case 1 · 分块过大——3800 字一整块，具体金额被"稀释"在长文本里，向量相似度就低。修法：分块调到 400-500 tokens，用 Document-aware 按"第 3 章 · 第 X 条"切开。

Case 2 · 元数据过滤缺失——用户明确说"2024 年"，你没用 metadata.publish_date 过滤。修法：加 parse_filters 抽年份，向量检索前先按年份过滤。

Case 3 · 缺重排——向量检索是粗筛，"综合评分法"这个词表面相似度最高的往往是"讲介绍"的那段。修法：加 Reranker（gte-rerank / BGE-Reranker-v2），Top-20 粗筛后重排取 Top-5，含权重的段会被排到前面。

面试金句："检索答错不要着急换模型——先诊断是哪个维度的问题。分块碎调分块、噪声多加阈值、顺序乱加重排、时间/来源相关就上元数据过滤。90% 的问题都在这 5 个维度里。"

📊 检索质量评估 SOP
  • 先建测试集——找 30-50 条真实用户问答对，标注"正确答案在哪个分块"。这是所有指标的前提。
  • Recall@K：命中标准答案分块的查询数 / 总查询数。反映"检得到吗"。
  • MRR：平均 (1 / 标准答案排名)。第 1 位命中 = 1.0，第 5 位命中 = 0.2。反映"排得靠前吗"。
  • NDCG：给每个候选打相关性分（0-3），算加权累计。反映"高相关的排得越前越好"。
  • 端到端答对率：跑完整 RAG，让人肉判分"答得对不对"。这是唯一直接跟客户对齐的指标。

PM 汇报口径："我们 Recall@5 是 89%，端到端答对率 88%。剩下 12% 里 60% 是知识库确实没有、40% 是 LLM 生成时抓错重点，下一版重点攻这两块。"——这种表述比只说"效果 88%"专业 10 倍。

📝 五、5 题小测验

建议先自己想 20 秒再点开答案。答错也别慌——错项解析比正确答案更值钱。

Q1 · 客户反馈 RAG 检不准，你的第一反应最不该是？
  • A. 把 Top-K 从 5 调到 20 看看
  • B. 检查分块结果，看有没有关键信息被切开
  • C. 建一批测试集，先量出 Recall@5 和答对率
  • D. 换一个更强的 Embedding 模型试试
✅ 答案：A

只调 Top-K 是治标不治本——治好召回了但塞进 LLM 的噪声也多了，答对率反而可能下降。正确顺序：先建测试集量化 → 再看分块和模型 → 加重排 → 最后才微调 Top-K。

❌ 错项解析

B 是对的第一反应——Day 7 的预处理是天花板，先排查这里。C 是最专业的第一反应——没测试集就没有量化改进，一切"感觉变好了"都是玄学。D 也可以是备选——如果是 OpenAI ada-002 的中文项目，换成 BGE-M3 或阿里云 v3 立刻能涨。但相比 A 更有针对性。

Q2 · 关于 Reranker（重排模型），下面哪种说法是错的？
  • A. Reranker 通常带来 10-15 个百分点的答对率提升
  • B. 用法是：向量粗筛 Top-20 → 重排取 Top-5 → 给 LLM
  • C. Reranker 可以完全替代 Embedding，直接对每个候选打分就行
  • D. 中文场景推荐 BGE-Reranker-v2 或阿里云 gte-rerank
✅ 答案：C

Reranker 是"精排"，性能比 Embedding 慢 10-100 倍，对每个候选都要跟 query 拼一起过一遍模型。库里几万分块不可能全走 Reranker，必须先用 Embedding 粗筛出 Top-N 再精排。两者是配合关系，不是替代。

❌ 错项解析

A 对——这是实践中常见的提升幅度，也是 Reranker 值得引入的理由。B 对——这是标准用法。D 对——中文场景这两个都是主流选择。

Q3 · 用户问"2024 年招标文件里哪些提到 ESG"，最优的检索策略是？
  • A. 直接把整个问句 embedding 后向量检索 Top-5
  • B. 先按 publish_date=2024 和 doc_type=招标 过滤，再对剩余分块做向量检索
  • C. 把 Top-K 调大到 30，让更多候选进 LLM
  • D. 让 LLM 直接扫描全库找"2024 + ESG"关键词
✅ 答案：B

这是元数据过滤前置的标准场景。用户问句里明确有"2024 年"和"招标文件"两个可结构化过滤的条件——先按 metadata 过滤缩小候选池，再对剩余分块做向量检索。既提高准确率、又省算力。

❌ 错项解析

A 是常见做法但不是最优——库里 2019-2023 年的 ESG 文档会一起被检出来，污染结果。C 只会引入更多噪声，不解决时间维度的问题。D 是最错的——LLM 没有全库扫描能力，也没这么用的。这就是 Day 7 元数据文化的价值兑现场景。

Q4 · 关于 4 个检索质量指标，哪一个最适合跟外行客户汇报？
  • A. Recall@K
  • B. MRR
  • C. NDCG
  • D. 端到端答对率
✅ 答案：D

端到端答对率是唯一"客户能听懂"的指标——直接对应"这个 AI 好不好用"。Recall/MRR/NDCG 都是工程指标，跟客户讲他会问"那到底对不对？"。PM 汇报口径：客户面前只讲答对率，技术复盘再拆到 Recall/MRR。

❌ 错项解析

A Recall@K 需要解释"K 是啥"——客户听着累。B MRR 更抽象——"倒数排名"这个概念普通业务方 5 分钟解释不清。C NDCG 是最技术的——甚至技术团队都要查公式。这三个都是内部复盘用，不是对外汇报用。

Q5 · 综合题——你手上的 RAG 端到端答对率 65%，客户要求 85%+，你的优化路线图应该怎么排？

按今天学的 5 个维度设计一版计划，说清每步预期收益和排序理由。

✅ 参考答案

第 0 步 · 建量化基准——先建 30-50 条测试集，跑一遍拿到当前 Recall@5、MRR、答对率。没这一步后面都是玄学。

第 1 步 · Chunk 调优——查当前分块参数。政企文档改到 400-500 tokens + 15% overlap，用 Document-aware。预期 +7-10。

第 2 步 · Embedding 选型——如果是 OpenAI ada-002 或 BGE-Base，换到 BGE-M3 或阿里云 text-embedding-v3。预期 +5-8。

第 3 步 · 相似度阈值——设 0.5-0.55，去噪。预期召回微降但答对率 +2-3。

第 4 步 · Reranker——加 gte-rerank 或 BGE-Reranker-v2。预期 +8-12（单步收益最大）。

第 5 步 · 元数据过滤——分析用户问句里能不能抽出时间 / 类型 / 来源关键词，前置过滤。预期 +2-4。

预期终局：65% → 85%+（假设每步收益按预估叠加，实际会有 10-20% 折损，但达标概率高）。

面试金句："RAG 优化不是玄学——先建测试集、按顺序调 5 个维度、每一步都能量化收益。这个套路我在两个国网项目里都跑通过。"

💼 六、面试金句预埋

检索决定天花板 "RAG 系统里，检索是天花板、生成是执行者。检索检不到，LLM 再牛也是编。我做 RAG 优化的顺序永远是先建测试集，再一步一步动 chunk / embedding / 阈值 / 重排 / 元数据过滤——五个维度，每一步都能量化收益。"
优化顺序意识 "很多同学一遇到检索不准就调 Top-K，其实这是最后一步。我的顺序是分块 → 嵌入模型 → 阈值 → 重排 → 元数据过滤——因为分块是天花板，模型是基础，重排单步收益最大。Top-K 只在最后微调，早调只会掩盖问题。"
元数据前置 "元数据过滤是 RAG 最被低估的优化——用户问'2024 年'的东西，你却让向量在 2019-2023 年的文档里挣扎。能用结构化字段解决的，别让向量硬拼。这一步单步收益不一定最大，但成本最低、最容易见效，是 PM 汇报的性价比之王。"

📓 心得笔记

⚠️ 今天最反直觉的 3 件事

1. Top-K 调大不是万能药——召回涨了、噪声也进来了，端到端答对率可能反而下降。（先建测试集才有话说。）

2. 中文场景默认用 OpenAI embedding 是最大坑——中文场景 BGE-M3 或阿里云 v3 完胜。

3. Reranker 是"性价比之王"——加一个模型就涨 10-15 个百分点，比调其他任何参数都值。（除非你已经加过了。）
